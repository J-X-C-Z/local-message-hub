# Avatars and Attachments

The WebUI shows an avatar when the synchronized contact or conversation record contains an avatar URL. Message senders inherit the avatar of a matching contact in the same platform account. Missing or unavailable images fall back to the first character of the display name.

Avatar URLs from platform records are metadata only. The browser accepts only same-origin paths, and the Hub serves a matching image only if it already exists in its local avatar cache. A cache miss never performs DNS or HTTP requests. Cached files are rechecked for a supported image signature and the 2 MiB limit; only the known QQ and WeChat/WeCom avatar hosts are accepted as cache keys. Missing local images fall back to the first character of the display name.

The WeChat provider reads avatar URL metadata only from the explicitly allowlisted contact columns used by the pinned WeFlow reader (`big_head_img_url`, `small_head_img_url`, and known camel-case aliases), after inspecting the actual contact-table columns. During explicit sync it also reads `head_image.db` only when that database has a loaded key and its schema exactly matches `head_image(username, md5, image_buffer, update_time)`. It matches by exact contact `username` (never inferred from `md5`), accepts only JPEG-signature blobs up to 2 MiB, caps a sync batch at 50,000 names / 32 MiB, and atomically copies accepted bytes into Hub-owned avatar storage. The local `hub-avatar://wechat/<sha256>` reference is bound to the WeChat account and username. Unknown schemas, locked databases, missing rows, or unsupported image bytes fail closed; no remote URL is fetched. Synthetic tests cover schema/key checks, exact identity, size/signature bounds, local-cache precedence, and source-read-only behavior.

The QQ local reader maps avatar identities only beneath the selected account's `nt_qq/nt_data/avatar` directory, rejects symlinks and paths outside that account root, reads at most eight contact images per sync, and caps each read at 2 MiB. The Hub then accepts only JPEG, PNG, GIF, or WebP signatures before atomically caching the bytes under its own avatar directory. It does not call QCE's avatar export action or fetch avatar URLs. A bounded check on the current machine returned cached images for QQ and WeChat; it did not verify that every contact has an image.

WeCom contact/roster readers currently expose avatar URL metadata only. There is no verified local WeCom avatar byte-cache reader, so the UI uses its initials fallback when the image is not already present in Hub's local cache. Do not fetch avatar URLs or infer a WeCom avatar-file mapping.

Image, video, voice, and file previews use resources that are already available in a platform's supported local cache or in the QQ roaming import cache. The WeCom reader joins the copied `CacheMapping.mapping` index to the decrypted `file_table4.md5`, then resolves only existing files under the configured account's `Cache` tree. Both databases are opened read-only; paths stay in provider memory and are revalidated before serving. Unknown schemas, missing mappings/files, and files outside the account cache remain unavailable. Synthetic linkage, path-redaction, and resolver tests pass; real-account WeCom preview/export still needs visual acceptance after running the updated build. Availability varies by platform, message type, and local cache state; the Hub does not claim that every historical attachment can be recovered.

MCP exposes attachment metadata through `list_media`, `get_message`, and message resources. An explicit `get_attachment` call can return one indexed, locally cached image, video, voice message, or file (maximum 8 MiB). Image/audio use MCP media content and video/files use a bounded embedded resource. Supported image/video/audio signatures are checked; PDF, ZIP, RTF, and OLE file signatures receive a matching MIME type while unknown files remain opaque. The reader never opens, executes, or extracts document bytes, and never fetches an attachment from a remote host. The MCP client may forward explicitly requested media or files to its configured model, so that transfer follows the client's privacy policy.
